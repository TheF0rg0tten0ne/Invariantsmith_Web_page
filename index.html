A local code-fixing assistant

Fixes you can check, on your own machine.

InvariantSmith runs a small fine-tuned model on your laptop and checks every fix before offering it. Your code never leaves the machine.

Get started How it works

What it does

An editor, and a fix loop you can trust.

Open a Python, C, or Java file. InvariantSmith reports the errors it finds and proposes a fix as a unified diff. You accept, reject, or ask for another attempt.

Analyse

Finds errors in Python, C, and Java files and lists them in the editor.

Propose

Suggests a fix as a diff. Some common errors are repaired by fixed rules, with no model involved, so those are fast and predictable.

Verify

Checks the fix before offering it. See what verification checks.

Decide and remember

Accept, reject, or regenerate. Every suggestion and its outcome is kept in a local SQLite history.

Missing address-of in scanf 
int n;printf("Enter a number: ");scanf("%d", n);scanf("%d", &n);printf("You entered %d\n", n);

Before: the second argument to scanf is missing &. Press Play to see the fix applied.

How it works

Five stages, and nothing is applied without a check.

  1. 01

    Analyse

    Scan the file and list the errors.

  2. 02

    Propose

    Produce a diff from a fixed rule or the local model.

  3. 03

    Verify

    Confirm the fix resolves the reported error and adds no new ones.

  4. 04

    Apply or reject

    You decide. Nothing changes until you accept.

  5. 05

    History

    The suggestion and its outcome are saved in SQLite.

What a "Verified fix" badge means

  • The reported error is no longer produced after the fix.
  • The fixed file does not produce new errors that the original did not have.

Verification confirms these two checks. It does not confirm that the fix matches your intent. It does not confirm that the fix matches your intent, so read the diff before you accept it.

Why a small local model

A trade-off, not a shortcut.

The model is a 1.5-billion-parameter Qwen2.5-Coder, fine-tuned with LoRA on 291 curated fix pairs. It is less capable than large cloud models. InvariantSmith makes up for that by checking its work instead of trusting it.

The held-out set is small (14 cases, all Python), so 13 of 14 is a signal, not a benchmark. The 274 of 291 result (94.2%) is on the training examples and measures how well the model memorized them, so it is not reported as accuracy.

Goals and aims

Make a small local model reliable enough for beginners.

The aim is a tool that students and beginners can run on ordinary hardware, and trust because it checks its own work.

Current capabilities

  • Live analysis of Python, C, and Java as you type.
  • Fixes shown as a diff, with a confidence badge and a Checks and Verification list.
  • Deterministic repairs for common beginner errors, without the model.
  • Converts whole programs between Python, C, and Java, with a side-by-side preview.
  • Run inside the editor, with stdin input and an Output tab.
  • A local SQLite history of every AI action and its outcome.

Roadmap (not current features)

  • Larger models on capable hardware.
  • More languages.
  • Wider deterministic repair coverage.
  • Better evaluation datasets.
  • Team and classroom features.

Getting started

From clone to your first verified fix.

Choose your operating system to see the matching commands. Each command has a copy button.

Requirements

  • Python 3.11 or newer (3.12 tested).
  • 8 GB RAM recommended. No GPU needed.
  • About 2 GB of free disk space for the stock model, or about 3.3 GB for the fine-tuned pair, plus the repository.
  • Optional: gcc and javac on your PATH for more accurate C and Java checks.
  • Git.

  1. 1. Clone the project and create a virtual environment

    git clone https://github.com/TheF0rg0tten0ne/Invariantsmith_seventh_sem_project.git
cd Invariantsmith_seventh_sem_project
python -m venv .venv

    Then activate it with the command for your system in the tabs above.

  2. 2. Get the model

    Place the model file in the models/ folder of the cloned repo. Pick one option.

    Option A: stock base model (about 2 GB, downloaded by a script).

    bash scripts/download_model.sh

    Option B: fine-tuned files (from the Google Drive folder). The server finds these by filename, with no configuration:

    • qwen2.5-coder-1.5b-fix.Q8_0.gguf, used for fixes and explanations.
    • qwen2.5-coder-1.5b-convert.Q8_0.gguf, used for conversion. If absent, the fix model is used. Each file is about 1.65 GB.

    If only the stock file is present, it is used for everything.

  3. 3. Install dependencies

    Install the server packages, then the client packages.

    pip install fastapi uvicorn pydantic pyflakes llama-cpp-python
    pip install -r client/requirements.txt

    The repository has no root requirements file for the server yet, so the server packages are listed above.

  4. 4. Start the server

    uvicorn server.main:app --host 127.0.0.1 --port 8731

    The model loads in the background. Check its state at http://127.0.0.1:8731/model/status.

  5. 5. Start the editor

    python -m client.main

  6. 6. Try it

    Open a .py, .c, or .java file with a known error. Click the underlined error or a row in the Problems panel, request a fix, and accept it if the diff looks right.

If the editor reports that the model is not loaded, check that the .gguf file is in models/ and restart the server. More answers are in the FAQ.

FAQ and troubleshooting

Common questions.

Does my code leave my machine?

No. The editor talks to a server bound to 127.0.0.1, and the model runs on your computer with no network access at inference time.

Why does it say "Model not loaded" (503)?

Check that a .gguf file with one of the expected names is in models/, then check /model/status. The first request also loads the model, which can take a while on CPU.

Why does it say the fix "no longer matches the current code" (409)?

The buffer changed after the fix was generated, so the fix was refused to protect your edits. Click Regenerate.

Why isn't every fix marked verified?

A fix is only marked verified if the reported error is gone and no new errors appear. Unverified fixes are still shown with their checks, so you can decide.

Why a small model instead of a large one?

It runs on ordinary laptops with no GPU and no cloud. See the trade-offs.

Fixing a large file is slow. What can I do?

Fix one error at a time. Long files are split into scoped chunks around the error, but a small model on CPU still takes time.

C or Java errors look wrong.

Install gcc and a JDK so the server uses the real compilers instead of its heuristic checker.
